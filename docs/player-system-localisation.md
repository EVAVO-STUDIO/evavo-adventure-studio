# Player system localisation

The Player governs its own presentation copy through one stable localisation adapter. This
includes the classic pause and save overlay, startup and loading chrome, transient status-rail
feedback, replay controls, cutscene skip guidance, the runtime language selector and Player
accessibility labels.

Gameplay dialogue, scene text and authored sequence captions continue to use their existing
project-localisation paths. The Player adapter only owns copy generated by the Player itself.

## Source contract

`@evavo/adventure-project-schema/localisation` exports:

```text
extractPlayerSystemLocalisableText(projectId)
playerSystemLocalisationKey(field)
canonicalPlayerSystemText(field, values)
formatPlayerSystemText(text, values)
```

The `playerSystem.*` catalogue covers:

- pause, save, load, options and return-to-title headings and controls;
- quick-save and numbered save-slot labels, summaries and notices;
- runtime loading, title-screen, restore and new-game startup states;
- status-rail feedback for save, load, resume and Player failures;
- replay recording, completion, export and failure feedback;
- cutscene fallback copy and localised keyboard skip hints;
- runtime language-selector copy and accessibility labels;
- the native game-canvas accessibility label.

Dynamic copy uses the normal `{placeholder}` grammar. Slot numbers, scene names, logical ticks,
scores, item counts, replay event counts, authored captions, sequence names and error messages are
supplied only at presentation time.

## Runtime resolution

After a runtime bundle is loaded, the Player resolves system copy from the selected locale pack.
A missing locale, missing key or runtime without a localisation pack falls back to canonical
English copy. The very first “loading runtime bundle” message necessarily uses canonical copy
because the project locale pack has not been fetched yet.

The language selector uses the same resolver as the rest of the Player. Selecting another locale
persists the preference and reloads presentation state without changing save compatibility.

Authored cutscene captions remain untouched. The Player only wraps them with a governed skip hint
when the sequence has reached its safe skip tick. A cutscene without a current caption uses the
localised sequence name or generic cutscene status instead.

## Readable transient feedback

The browser status rail previously refreshed from gameplay state every animation frame. As a
result, messages such as “game saved”, “replay exported” and “cutscene skipped” could disappear in
a single frame.

`createPlayerStatusRail` now separates three operations:

```text
replace(text)    deliberate status change; clears any hold
announce(text)   transient feedback; held for 1.8 seconds by default
refresh(text)    render-loop baseline; ignored while an announcement is held
```

The default hold is 1.8 seconds. Failure messages that include diagnostic detail use a 4.2-second
hold. Both are wall-clock presentation state only and are not written into game state, saves,
replays or deterministic frame data.

## Determinism boundary

Player localisation must not make locale selection affect simulation or persistence. Therefore:

- menu item IDs, slot numbers, compatibility checks and state transitions are unchanged;
- replay event data and final fingerprints are unchanged;
- cutscene timing and safe-skip policy are unchanged;
- transient status holds do not pause or alter logical ticks;
- gameplay status stored in canonical save interface state is intentionally not translated by
  this adapter.

That final boundary is deliberate: translating saved gameplay status during controller execution
would make otherwise identical saves differ by locale. Those messages can be migrated later only
with a key-based save schema rather than storing rendered copy.

## Compatibility policy

Player system text remains opt-in for existing localisation manifests. A manifest opts in when any
target locale contains a `playerSystem.*` entry.

After opt-in:

1. the compiler adds the complete canonical Player system catalogue to the runtime locale pack;
2. draft locales may use source fallback;
3. review locales report missing Player copy as warnings;
4. release locales must translate the complete Player catalogue;
5. placeholder mismatches remain compilation errors.

A legacy manifest with no `playerSystem.*` entries remains source-compatible and uses canonical
English Player copy.

## Studio authoring and text fit

Localisation Studio includes Player system entries beside project, front-end and lifecycle text.
New target locales receive complete entries and pseudo-localisation can pressure-test every Player
surface. The governed roles are:

```text
player-system-heading
player-system-description
player-system-menu-label
player-system-status
player-system-footer
```

Loading strings, replay counts, cutscene hints and transient notices use the existing native bitmap
text-fit audit rules. The Studio fixture includes representative French translations for the
expanded runtime surface.
